# Test-to-requirement traceability

Source: the requirement rows in [`specs/srs_data.py`](specs/srs_data.py). This is a map of **test evidence**, not a claim that the implementation meets every requirement. The SDS is useful design context but its test counts and some implementation notes are stale. The Python data files are read as text; this matrix does not execute them.

Status meanings:

- **Direct**: a test exercises the stated behavior through a real application module or browser flow. It may still need more edge cases.
- **Partial**: a related behavior is tested, but a material part of the requirement is not proved.
- **Open**: no current test proves the requirement.
- **Mismatch**: the current implementation or test contract differs from the SRS; adding a passing test for the current behavior would not close the requirement.

The test paths below link to representative evidence. A browser smoke test only proves that a page and its live query work; it does not prove the full transaction behind the page. Assertions against test-local helper functions are not counted as evidence for application service behavior.

E2E source-line coverage is not collected and must not be added to frontend percentages.

Normal PR/push CI runs tests without coverage and runs the root browser suite once against an isolated database; it typechecks browser tests and rejects skipped or unexpected browser results. It does not upload browser diagnostics or run the traceability checker. Developers can collect backend/frontend coverage and check the regression floors themselves using the [manual commands](../tests/README.md#manual-coverage-commands); there is no coverage workflow. Backend tests run once rather than repeating item/admin subsets. The normal backend CI build generates the current Prisma client in its disposable checkout; the local isolated runner generates/compiles a copy under `tests/.artifacts` so repository `src` remains untouched. These local results do not prove a GitHub-hosted workflow run has completed.

## Important additions in this work

- Real browser journeys for T2 approval, borrower collection, extension, independent inspection, appeal evidence/credit restoration and repair; real same-day room booking/check-in/photos/return.
- Frontend registration/token/password/profile pages, pickup/room-use photo guards and repair/room-check pages call real application hooks. Mocking is restricted to the API boundary; responses use backend schemas.
- Real cron methods for overdue/loss/expiry/reminders and notification event recipient/dedupe contracts. Worklists, repair/history filtering and extension cancellation/privacy now have edge cases.
- Removed conditional E2E skips and mandatory-fixture fallbacks. A fixed business clock controls browser/backend time without slowing timers. API bodies are buffered before navigation; batch responses and delete contracts are checked correctly.

## Remaining limits and product defects

1. Five executable known-defect checks remain: catalogue popularity uses stock totals, catalogue unit-tag search loses a real item, logout leaves another borrower's cart, the stock checklist stays green after a window clash, and damage inspection emits no credit-deduction notification. No `src` changes were made to resolve these product behaviors. The complete 39-case browser run had no skips; its reporter counts the two expected failures among 39 successful outcomes.
2. Full approval history is deferred by SRS v1.1; semester bounds, G1/G2 alternatives and the listed renewal/penalty/allocation mismatches still require implementation/policy work. Passing tests of current behavior do not resolve mismatches.
3. OAuth exchanges, delivered email, deployed TLS, backups, uptime, cross-browser operation and production-scale performance require separate evidence.
4. Browser line coverage is not collected. Unit mocks do not prove every database interaction; real journeys cover representative cases, not every permutation of tier/credit/role.

## Latest performance run

The isolated local k6 run on 27 September 2026 passed: 2,880 HTTP requests (one setup login and 2,879 status queries), p95 11.07 ms, 0% HTTP failures and 100% valid system-status responses. All 8,637 checks passed. The 110-second profile ramps from 0 to 20 to 50 virtual users, then down to 0; it does not sustain 50 users for a full minute. Thresholds are p95 < 250 ms, HTTP error rate < 1% and valid API responses > 99%.

Evidence: `tests/.artifacts/load-summary.json` (ignored local artifact). The test database and temporary uploads were removed afterward. These measurements are from the local run. CI now runs the same status-endpoint profile in the separate `admin system load` job; no GitHub-hosted performance result has been established here. It measures only `admin.getSystemStatus` against seed-sized data and does not prove production capacity or all performance requirements.
