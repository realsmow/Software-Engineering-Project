# `specs/` — SRS และ SDS ฉบับ Word และ PDF

โฟลเดอร์นี้สร้างเอกสารสองฉบับที่ **อาจารย์เปิดใน MS Word ได้จริง** พร้อม PDF
ที่แปลงมาจากไฟล์ `.docx` ตัวเดียวกัน (ไม่ใช่คนละต้นฉบับ)

> เอกสารอื่นทั้งหมดของโครงการเขียนด้วย LaTeX ที่ `docs/` — ดู `docs/INDEX.md`
> ที่นี่ใช้ Word เพราะโจทย์คือ "ต้องแก้ต่อในเวิร์ดได้"

## วิธีสร้าง

```bash
cd docs/specs
uv run --with python-docx --python 3.12 python gen_srs_docx.py
uv run --with python-docx --python 3.12 python gen_sds_docx.py
```

ผลลัพธ์ออกที่ `docs/build/` ทั้งสี่ไฟล์

| ไฟล์ | คืออะไร |
|---|---|
| `build/ULMs-SRS-v1.0.docx` / `.pdf` | ข้อกำหนดความต้องการ 21 หน้า |
| `build/ULMs-SDS-v1.0.docx` / `.pdf` | ข้อกำหนดการออกแบบ 40 หน้า |

## โครงเอกสารมาจากสไลด์ของวิชา ห้ามเปลี่ยนเอง

- **SDS** → `resource/Week 09 - System Design Specification 2569-08-27 R12.pdf` สไลด์ 29–33
  กำหนดหัวข้อ 1–11 ไว้ตายตัว (General Product Description → Back-out Procedure)
  `sds_data.py` เรียงตามนั้นทั้งหมด **เพิ่มหัวข้อย่อยได้ แต่อย่าสลับหรือตัดหัวข้อหลัก**
- **SRS** → `resource/Week 05 - Requirements Gathering 2569-07-23 R10.pdf` กำหนดกรอบ IEEE 830-1998
  `srs_data.py` เรียงตามนั้นแล้ว **หัวข้อ 1.5, 2.1.1-2.1.8, 2.6, 3.3, 3.5, 3.6 เขียนเพิ่มใหม่**
  เพราะฉบับของทีมไม่มี ส่วนความต้องการทุกข้อยังเป็นของทีมคำต่อคำ

| `doc_builder.py` | รูปแบบทั้งหมด (ฟอนต์ ตาราง สารบัญ หัว-ท้ายกระดาษ แปลง PDF) |

> (ตัดหน้าสรุป · หัวข้อ 1.3 · 1.4 · ภาคผนวกสอบทาน และปรับถ้อยคำหลายจุด · 3 ก.ย. 19:40)
> **การรัน `gen_sds_docx.py` จะทับทิ้งทันที** สำรองไว้ที่ `build/ULMs-SDS-v1.0.BACKUP-ก่อนซ่อม.docx`
> ถ้าจะกลับไปใช้ generator ต้องย้ายการแก้เหล่านั้นเข้า `sds_data.py` ก่อน

## ถ้าจำเป็นต้องแก้ด้วยมือใน LibreOffice

คัดลอกออกจาก `build/` ก่อน (เช่นไป `docs/submit/`) แล้วแก้ที่สำเนานั้น
ให้สำเนากลายเป็นตัวจริงของรอบส่งนั้นไป มิฉะนั้นการรัน generator ครั้งถัดไปจะทับทิ้ง

**เซฟเป็น `.docx` (กด "Use Word 2007-365!") ไม่ต้องผ่าน `.odt`** — ทดสอบ round-trip
ไฟล์จริงแล้วทั้งสองเส้นทางให้ผลเท่ากันเป๊ะ: 40 หน้าเท่าเดิม ฟอนต์ที่ฝังชุดเดียวกัน
สารบัญยังเป็นฟิลด์จริง เลขหน้ายังเป็นฟิลด์ หน้าแนวนอน หัวตารางซ้ำข้ามหน้า และแถวที่ห้ามฉีก
อยู่ครบทั้งคู่ ODF จึงไม่ได้รักษาอะไรเพิ่ม มีแต่เพิ่มรอบแปลง

**สิ่งที่หายทั้งสองเส้นทางคือ `updateFields`** ซึ่งเป็นตัวสั่งให้ Word รีเฟรชสารบัญเองตอนเปิด
หลังแก้ในLibreOffice ต้องอัปเดตสารบัญเอง — คลิกขวาที่สารบัญ → **Update Index**
(หรือ Tools ▸ Update ▸ Update All) **ก่อน** export PDF ไม่งั้นเลขหน้าในสารบัญค้างของเดิม
และอย่าลืม export PDF จากไฟล์ที่แก้แล้ว มิฉะนั้น Word กับ PDF ที่ส่งจะไม่ตรงกัน

## สิ่งที่ต้องมีในเครื่อง

- **ฟอนต์ Sarabun** — ตัวเดียวกับที่ระบบใช้ ถ้าไม่มี Word และ LibreOffice
  จะแทนด้วยฟอนต์อื่นและหน้าจะเลื่อน ติดตั้งจาก
  <https://fonts.google.com/specimen/Sarabun> ลงใน `~/.local/share/fonts/`
  (เครื่องนี้ลิงก์ไว้ที่ `~/.fonts/Sarabun` ให้แล้ว) แล้วสั่ง `fc-cache -f`
- **LibreOffice** (`soffice`) — ใช้แปลง `.docx` เป็น `.pdf`
- **uv** — ดึง `python-docx` มาใช้ชั่วคราวโดยไม่ต้องติดตั้งถาวร

## สามเรื่องที่ต้องรู้ก่อนแก้ `doc_builder.py`

1. **ภาษาไทยใน Word เป็น "complex script"** — Word อ่านฟอนต์และขนาดของข้อความไทย
   จากแอตทริบิวต์ `w:cs` / `w:szCs` / `w:bCs` ไม่ใช่ตัวปกติ ทุกฟังก์ชันจึงเซ็ตทั้งคู่
   ถ้าลืม ข้อความไทยจะกลายเป็นฟอนต์อื่นขนาดอื่นทั้งที่ภาษาอังกฤษยังถูก
2. **ความกว้างคอลัมน์ต้องเขียนลงตารางกริด** (`w:gridCol`) ไม่ใช่แค่ที่ช่อง —
   เมื่อใช้ layout แบบคงที่ ทั้ง Word และ LibreOffice วัดจากกริด
3. **สารบัญสร้างสองรอบ** — รอบแรกได้ PDF ที่มีจำนวนบรรทัดถูกแต่เลขหน้ามั่ว
   อ่านกลับมาว่าหัวข้อไหนตกหน้าไหน แล้วสร้างใหม่ด้วยเลขจริง
   ฝั่ง Word ยังเป็นสารบัญของจริงที่กด F9 อัปเดตได้ ส่วน PDF ได้เลขหน้าที่ถูกต้อง
   เพราะ LibreOffice เรนเดอร์จากค่าที่ฝังไว้ ไม่ได้คำนวณสารบัญใหม่เอง

  (`schema.prisma`, `backend/src/`, `frontend/src/`, `.github/workflows/ci.yml`)
  ส่วนที่ยังไม่ได้ทำระบุไว้ในคอลัมน์ "สถานะ" และภาคผนวก ค
